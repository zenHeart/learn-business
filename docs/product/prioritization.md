# 优先级与取舍框架

> 框架是"把争论变成数字"的沟通工具，不是优化器。选哪个框架，取决于你在什么场景下需要说服谁——包括说服自己。

## 三大评分框架

### RICE（Intercom）

```
RICE = (Reach × Impact × Confidence) / Effort
```

| 维度 | 含义 | 单位 |
|---|---|---|
| Reach | 一个时间段内触达的用户数 | 人/季度 |
| Impact | 对单个用户的影响程度 | 量表 0.25~3 |
| Confidence | 对以上估计的信心 | 量表 50%/80%/100% |
| Effort | 投入的人月 | 人月 |

**适用**：同一转化目标下、触达可量化的功能 backlog——增长/转化团队的排序工具。

**已知局限**（含框架作者本人的声明）：

- Intercom 原文明确写了"这不是硬规则"（not a hard rule）
- Impact 仍是主观量表——乘法运算制造**伪精确**
- 不含延迟成本：晚做三个月和早做，分数一样
- 依赖项和大赌注项目会被系统性压分

### ICE（Sean Ellis《Hacking Growth》）

```
ICE = Impact × Confidence × Ease    // 各 1~10 分
```

**适用**：增长实验的**快筛**——在几十个实验想法里快速分桶，而不是排季度路线图。

**已知局限**：

- 完全主观，分数会随填写人的状态通胀
- Ease 维度会扼杀"难但大"的想法——按 ICE 排序的团队永远做小实验
- 无 Reach（不管影响多少人）、无战略对齐

### WSJF（SAFe，源自 Reinertsen《Principles of Product Development Flow》）

```
WSJF = CoD / Job Size
CoD（延迟成本）= 业务价值 + 时间紧迫性 + 风险降低/机会赋能
```

**适用**：有明确时间窗口（监管期限、竞争时序、节日窗口）的企业特性排序。

**已知局限**：

- SAFe 用相对 Fibonacci 估算把不同量纲加总，偏离了原著以货币计的延迟成本
- "延迟成本线性"假设常不成立
- 大平台型/创新项目被系统性压低

## 给自己拍板：轻量三问

个人决策（给自己排优先级）不需要全套 RICE。三个问题按顺序回答，答案写下来：

1. **不做会怎样？**（延迟成本：3 个月后这条还重要吗）
2. **最便宜的验证是什么？**（能否用 1 天而不是 1 个月证伪）
3. **我在回避什么？**（如果是"怕判断错"而不是"信息不够"，评分框架救不了你——见[数据 vs 判断力](./data-vs-judgment)）

## 已知局限（总）

三套评分框架的共同问题：它们把**结构化讨论**伪装成**计算**。分数的价值在于让假设显式化、可被挑战，而不是分数本身。两个团队对同一批需求打分，分数分歧的地方就是需要讨论的地方。

## 给自己的锚点

- 下次排优先级时，先写"不做会怎样"，再看要不要上框架
- 一季度复盘一次：上季度排 Top3 的假设，哪些被打脸了？打脸原因记进 [复盘笔记](/management/okr)
